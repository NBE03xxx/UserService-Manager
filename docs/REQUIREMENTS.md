# 要件定義

## 1. 目的と用語

一般ユーザーが自分の `systemd --user` サービスを、端末操作に不慣れでも安全かつ予測可能に管理できる GUI を提供する。

- **発見済み**: 発見起点に存在し、systemd user manager から認識可能なサービス
- **管理対象**: 発見済みサービスのうち、ユーザーが本アプリでの管理を明示登録したもの
- **ユーザー領域**: ユーザーのホーム配下にあり、正規化・シンボリックリンク解決後も許可範囲内にあるパス
- **表示のみ**: status、ログ、詳細は閲覧できるが、状態変更操作はできない状態
- **システム実行基盤**: Ubuntu のパッケージ管理下にあり、root 所有かつ一般ユーザーが書換不能なインタプリタ、シェル、ランタイム等
- **ユーザーワークロード**: ユーザーが管理するスクリプト、実行ファイル、作業ディレクトリ、設定ファイル等
- **見つからない**: 登録情報は存在するが、現在のスキャンではユニットを確認できない状態

優先度は Must / Should / Could。v0.1 で Must を受入必須とする。

## 2. 機能要件

| ID | 優先度 | 要件 | 受入条件 |
|---|---|---|---|
| FR-001 | Must | `.service` の発見起点を `~/.config/systemd/user/` とする | 起点外に単独で置かれた未登録ファイルを候補表示しない |
| FR-002 | Must | 発見起点のユニットを systemd user manager の認識・読込状態と照合する | 正常なユニットは登録候補となり、読込エラーのユニットは理由付き表示専用候補となる。起点外の孤立ファイルは候補にしない |
| FR-003 | Must | 発見済みサービスをユーザーが明示登録できる | 登録前は管理一覧に入らず、登録後は再起動後も保持される |
| FR-004 | Must | 登録済みサービスが削除・認識不能になった場合、登録情報を保持して「見つからない」と表示する | 再スキャン後は操作不能となり、通知される。再出現時は登録状態が自動復元され、ユーザーは明示的に登録解除できる |
| FR-005 | Must | 外部での追加・削除・状態変更を起動時および手動再スキャンで反映する | 再スキャン後の表示が systemd の状態と一致する |
| FR-006 | Must | 一覧にサービス名、Description、Active 状態、Enable 状態を表示する | 各列が取得不能時の代替表示を含め描画される |
| FR-007 | Must | 管理可能サービスを start/stop/restart できる | 実行結果を再取得し、成功・失敗を表示する |
| FR-008 | Must | 管理可能サービスを enable/disable できる | 実行後の enable 状態を再取得して表示する |
| FR-009 | Must | サービスの status と主要詳細（ユニットパス、ExecStart 等）を表示する | 読み取り可能な情報を詳細画面で確認できる |
| FR-010 | Must | `daemon-reload` を明示操作として提供する | 確認後に user manager へ実行し、結果を通知する |
| FR-011 | Must | 対象サービスの journal ログを読み取り表示する | 選択サービス以外のログを混在させず、独自保存しない |
| FR-012 | Must | 参照先を役割別に評価し、ユーザー管理対象が領域外にあるサービスを表示のみにする | 信頼できるシステム実行基盤は領域外でも許容し、ユーザーワークロードまたは設定が領域外なら status・詳細・ログのみ利用可能となる |
| FR-013 | Must | ホーム内を指すシンボリックリンクは通常候補として扱う | 解決後の全参照先が許可範囲なら管理可能と判定できる |
| FR-014 | Must | ホーム外を指すシンボリックリンクは表示のみにする | リンク名がホーム内でも解決先が外なら変更操作できない |
| FR-015 | Should | 参照先判定の補助範囲をユーザーが追加・削除できる | 設定が永続化され、サービス発見範囲は増えない |
| FR-016 | Must | 読取・操作失敗を利用者向けメッセージと診断情報に分けて示す | UI は簡潔な理由を示し、診断情報をコピーできる |
| FR-017 | Must | 操作中の多重実行を防ぎ、完了後に状態を再取得する | 同一サービスへの競合操作が UI から送信されない |

## 3. 安全性・権限要件

| ID | 優先度 | 要件 | 受入条件 |
|---|---|---|---|
| SEC-001 | Must | 一般ユーザー権限のみで動作する | `sudo`、root、権限昇格を要求しない |
| SEC-002 | Must | systemd 操作は引数配列または D-Bus API を用い、シェル文字列連結をしない | 任意文字を含むユニット名でもコマンド注入がない |
| SEC-003 | Must | ユニット名とパスを検証・正規化してから利用する | パストラバーサルや別ユニットへのすり替えを拒否する |
| SEC-004 | Must | 操作直前にパス、リンク解決先、管理登録、現在の可操作性を再検証する | スキャン後の差し替えで制限を回避できない |
| SEC-005 | Must | 変更操作を許可リスト方式で制御する | 表示のみサービスには start/stop/restart/enable/disable を許可しない。daemon-reloadは個別unitから分離し、現在ユーザーのuser managerに対する確認済み全体操作としてのみ許可する |
| SEC-006 | Must | アプリ設定・登録情報をユーザー設定領域に保存し、安全な権限で扱う | 他ユーザーが書換可能な設定を信頼しない |
| SEC-007 | Must | ログやエラー表示で機密性の高い環境値を不用意に展開しない | Environment の値は既定で伏せるか限定表示となる |

## 4. UI・品質・互換性要件

| ID | 優先度 | 要件 | 受入条件 |
|---|---|---|---|
| UI-001 | Must | 一覧から状態と利用可能操作を理解できる | 色だけに依存せず文字・アイコン・ツールチップで示す |
| UI-002 | Must | 表示のみの理由を UI に明示する | 無効ボタンに理由があり詳細でも確認できる |
| UI-003 | Must | 破壊性・影響のある操作を適切に確認する | stop、restart、disable、daemon-reload は確認または設定可能な安全措置を持つ |
| UI-004 | Should | キーボード操作、フォーカス、支援技術向けラベルを備える | マウスなしで主要フローを完了できる |
| UI-005 | Should | 「おしゃれな午後の喫茶店でのひととき」を想起させる、穏やかで上質な視覚デザインとする | 温かみのある色、余白、控えめな質感で一貫して表現し、GNOMEとの調和、可読性、コントラスト、状態識別を損なわない |
| UI-006 | Must | 外観を「システム設定に従う」「ライト」「ダーク」から選択できる | 初期値はシステム設定に従い、システム外観の変化を反映する。手動選択は再起動後も保持され、両モードで全機能を利用できる |
| NFR-001 | Must | Ubuntu/GNOME/Wayland を第一対象とし GTK 系で構成する | Ubuntu 26.04 LTS を第一検証環境として主要受入試験が完了する。追加の最低対応 LTS は技術調査後に定める |
| NFR-002 | Must | UI をブロックせず状態取得とログ読込を行う | 通常操作中にウィンドウが応答不能にならない |
| NFR-003 | Should | systemd や journal が利用不能な場合に安全に縮退する | クラッシュせず原因と対処候補を示す |
| NFR-004 | Should | 設定形式にスキーマ版を持たせる | 将来の移行を判定できる |

## 5. 国際化・拡張要件

| ID | 優先度 | 要件 | 受入条件 |
|---|---|---|---|
| I18N-001 | Must | 日本語 locale は日本語、それ以外は英語を既定とする | 対応 locale で再起動時に正しい言語となる |
| I18N-002 | Must | UI 文字列をソースから分離し翻訳可能にする | ハードコード文字列の検査を通る |
| I18N-003 | Should | 後から手動言語選択を追加しやすい設定構造とする | `system/ja/en` 相当の値を追加可能である |
| EXT-001 | Must | ユニット種別と操作能力を分離した設計にする | `.timer/.socket/.path` を既存 service ロジックの全面改変なしに追加可能 |
| EXT-002 | Should | cron を別バックエンドとして追加可能にする | systemd 固有 API が UI 層へ直接漏れない |

## 6. v0.1 対象外

- `.service` の新規作成、元ファイル編集、削除
- `systemctl --user edit` 相当の drop-in 作成・編集、複数 drop-in 管理
- 編集時バックアップと systemd による構文検証
- `.timer`、`.socket`、`.path`、cron の管理
- journal の複製・独自保存
- root/system service の管理

これらは要件の否定ではなく、後続ロードマップへ延期する。
