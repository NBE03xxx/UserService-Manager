# フェーズ5 実装・検証結果

## 1. 状態

対象unit限定のjournal取得、ページング、ログ画面、検索、コピー、更新を実装し、2026-08-27にUbuntu 26.04 LTS / GNOME / Waylandで確認した。フェーズ5は完了とする。

ログ本文はアプリ独自に保存・複製しない。クリップボードへのコピーはユーザーの明示操作時だけ行う。

## 2. 実装内容

- `python3-systemd`のReaderを専用ワーカースレッドで実行
- canonical UnitIdと現在UIDによる限定
- `(_UID AND _SYSTEMD_USER_UNIT) OR (_UID AND USER_UNIT)`の二分岐match
- 新しい順、既定100件、最大200件の取得制限
- cursorによる過去ページ取得と境界項目の重複排除
- Reader異常時にも終了する読み取り試行回数上限
- MESSAGEのUTF-8安全変換と8,192文字上限
- priorityを0〜7へ正規化
- 日時、priority、本文を表示する独立ログ画面
- 読み込み済み範囲の検索
- 過去ログの追加読込
- 表示中ログの明示的なクリップボードコピー
- 更新、空状態、失敗状態、更新完了時刻
- ログ画面を閉じた後の遅延結果を反映しないgeneration管理

## 3. 自動テスト

全46件が成功した。フェーズ5固有の試験には次を含む。

- UIDと二種類のuser-unit fieldによるOR match
- 件数上限、has-more、older cursor
- ページ境界cursorの重複排除
- binary MESSAGE、不正priority、巨大MESSAGEの安全な正規化
- read-onlyの発見候補でもログを閲覧可能
- 未発見unitのログ要求拒否

Codexの制限環境ではワーカースレッド通知FDの作成が拒否されるため、adapterの同期中核を単体テストした。通常ログインセッションでは非同期経路を実機確認した。

## 4. 実機検証

既存の`script-runner.service`を読み取り専用で検証した。

- 第1ページ: 20件
- `has_more=True`
- priority: 6
- 最大表示メッセージ長: 111文字
- 切り詰め: 0件
- 第2ページ: 20件
- ページ間cursor重複: 0件
- ログ本文の端末出力・保存: なし
- サービス変更: なし

GUIではログ画面の表示、更新、過去ログ追加、検索、コピー、閉じた後のメイン画面を確認した。ログが増えていない場合に更新結果が分かりにくかったため、件数の横へ更新完了時刻を追加し、更新ボタンで時刻が変わることを再確認した。

## 5. 安全上の結論

- unit名は`UnitId`で検証済みの値だけをjournal adapterへ渡す。
- shellや`journalctl`文字列連結を使用しない。
- 別ユーザーまたは別unitの同名・類似ログをmatchへ混入させない。
- 件数と1メッセージ長の両方を制限する。
- UIスレッドでjournalを走査しない。
- journal本文を設定・キャッシュ・独自ログへ永続化しない。
